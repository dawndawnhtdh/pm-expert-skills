# 报告设计原则

## 1. 先确定汇报对象

报告写作前必须先回答：

| 问题 | 判断要求 |
|------|---------|
| 谁读 | 高管、决策者、客户、研究团队、评审委员会或内部产品评审 |
| 为什么读 | 判断态势、识别风险、决定是否投入、安排补证、准备复核 |
| 不解决什么 | 不替代正式决策、法律结论、线下核验或行动方案 |
| 证据条件 | 哪些判断有原始证据，哪些只是线索，哪些必须降级 |

报告应围绕读者的决策问题组织，而不是围绕数据字段组织。

## 2. 报告的四层结构

| 层级 | 作用 | 常见内容 | 放置位置 |
|------|------|---------|---------|
| 决策层 | 让读者快速知道本期最重要判断 | 综合研判、核心发现、重点变化 | 正文前部 |
| 分析层 | 解释为什么得出判断 | 格局分析、主题矩阵、风险路径、数据验证 | 正文主体 |
| 监测层 | 告诉读者下一步看什么 | 建议、补证方向、专题准备 | 正文后部 |
| 审计层 | 让判断可复核 | 结论-证据映射、来源包、原始数据、口径说明 | 附录 |

正文越靠前越应该像咨询判断，越靠后越可以承载结构化信息和审计内容。

## 3. 每章必须服务一个决策问题

设计章节时使用以下结构：

```text
章节名称
  -> 决策问题
  -> 必要输入
  -> 分析动作
  -> 输出判断
  -> 证据要求
  -> 降级规则
```

不要按"平台、账号、语种、地区"等数据字段直接堆章节。数据字段应服务于更高层问题，例如"竞争格局""风险路径""市场验证""专题研判"。

## 4. 正文和附录的边界

正文应保留：

- 核心判断；
- 对读者的影响；
- 必要证据编号；
- 必要数据，但只在数据改变判断时进入正文；
- 监测、补证、核验和专题准备建议。

附录应承载：

- 完整证据链；
- 原始来源和参考链接；
- 指标定义；
- 数据来源和限制；
- 负面边界；
- 分析框架；
- AI加工过程或审计说明。

## 5. 报告质量不是"更长"

高质量报告的标准是：

```text
判断更清楚
证据更贴近判断
边界更稳
章节更少但更有用
表格更少但更能比较
建议更像决策参考而不是派工命令
```

如果一段内容不能帮助读者判断态势、识别风险、复核证据或安排下一步工作，应删除、合并或移入附录。
