# 产品经理内容质量检查器

## 定位

这是专为产品经理设计的内容质量检查工具。覆盖 PM 日常输出的所有文档类型，帮助你和团队确保每一份输出都达到专业标准——不只是"写完了"，而是**问题清晰、方案可执行、metrics 可衡量、风险有预判、读者能行动**。

---

## 快速参考卡

```
1. 确定内容类型 → 2. 选择检查深度 → 3. 按框架逐层检查
   → 4. 门禁评估（✅/⚠️/❌/N/A）→ 5. 总体评估 + Top 3 修复
```

**三档检查深度：**

| 深度 | 耗时 | 适用场景 |
|------|------|---------|
| 快速 | 2-3分钟 | 日常邮件、Slack、会议记录 |
| 标准 | 5-10分钟 | PRD 初稿、策略文档、分析报告 |
| 完整 | 15-20分钟 | 高利害文档、对外交付、跨部门对齐 |

---

## PM 内容类型

| 类型 | 典型文档 | 检查重点 |
|------|---------|---------|
| PRD / Spec | 产品需求文档、功能规格、技术方案 | 问题定义、scope 纪律、用户场景覆盖、metrics |
| 策略与路线图 | 产品策略、路线图、OKRs、年度规划 | 逻辑闭环、对齐公司目标、取舍清晰 |
| 分析报告 | 竞品分析、用户研究、数据分析、市场调研 | 证据质量、样本代表性、结论可信度 |
| 决策文档 | 方案评估、trade-off 分析、go/no-go 建议 | 选项完整性、判断标准、风险和 mitigation |
| 沟通与同步 | 周报、立项同步、Launch 公告、stakeholder 更新 | 读者适配、核心信息突出、行动明确 |
| 会议输出 | 会议纪要、design review 总结、action items | 决策记录、责任人明确、闭环跟踪 |
| 用户触达内容 | Release notes、帮助文档、App Store 文案 | 用户视角、非技术表达、完整清晰 |

## 质量门禁（PM 专用）

### 1. 定位层（写给谁、解决什么）

| Gate | 校验目标 | 失败条件 | 处理 |
|------|---------|---------|------|
| PM-POS-01 | 读者明确 | 不清楚文档写给谁（工程？设计？高管？客户？），语气/粒度/结构不对 | 根据目标读者调整结构、术语密度和信息颗粒度 |
| PM-POS-02 | 问题先行 | 直接跳到方案，没有先说清楚"为什么做这个" | 前置 problem statement 段落 |
| PM-POS-03 | 边界清晰 | 没有说明 out-of-scope，或 scope 模糊到无法判断是否完成 | 补充明确的 in-scope / out-of-scope 列表 |
| PM-POS-04 | 上下文完整 | 新读者无法理解前因后果（缺背景、缺链接、缺决策历史） | 补充背景段落或引用相关文档 |

### 2. 产品基线层（核心问题闭环）

| Gate | 校验目标 | 失败条件 | 处理 |
|------|---------|---------|------|
| PM-PROD-01 | 问题→方案闭环 | 说清楚了问题但没给方案，或给了方案但不知道为什么解决这个问题 | 确保每个问题都有对应的方案方向 |
| PM-PROD-02 | Metrics 明确 | 缺少成功指标，或指标不可衡量（如"提升用户体验"） | 补充 SMART 指标 + 失败阈值 |
| PM-PROD-03 | 有优先级 | 所有内容同等权重，读者不知道什么最重要 | 补充优先级排序或 TL;DR |
| PM-PROD-04 | 格式匹配场景 | PRD 写成了技术方案，周报写成了散文，分析没有结论 | 调整为该文档类型的标准结构 |
| PM-PROD-05 | 自循环 | 发现上述问题后仍直接交付，不修复 | 自动修复后复评，最多 3 轮 |

### 3. 分析层（判断质量）

| Gate | 校验目标 | 失败条件 | 处理 |
|------|---------|---------|------|
| PM-ANA-01 | 结论先行 | 先堆数据/背景/过程，核心结论藏在最后 | 核心结论移到开头，背景后置 |
| PM-ANA-02 | 数据→判断闭环 | 有数据无解读，或数据支撑不了结论 | 补充"数据说明了什么" |
| PM-ANA-03 | 替代方案 | 只推荐了一条路，没考虑其他可能性 | 补充备选方案及取舍理由 |
| PM-ANA-04 | 用户视角 | 只从业务/技术角度分析，缺少用户视角 | 补充用户影响或用户反馈依据 |

### 4. 支撑层（依据可信）

| Gate | 校验目标 | 失败条件 | 处理 |
|------|---------|---------|------|
| PM-EVD-01 | 主张有依据 | 断言性陈述（"用户想要""市场需要""竞品在做"）没有来源 | 补充数据、研究引用或用户反馈 |
| PM-EVD-02 | 来源可查 | 引用了数据或研究但不注明来源 | 补全来源 |
| PM-EVD-03 | 代表性与局限 | 用了少量用户反馈代表整个用户群，或样本偏差未说明 | 说明样本范围和局限性 |
| PM-EVD-04 | 假设明确 | 关键假设不写出来（"假设用户 onboarding 完成率提升 20%"） | 列出关键假设及验证方法 |

### 5. 风险与边界层

| Gate | 校验目标 | 失败条件 | 处理 |
|------|---------|---------|------|
| PM-RISK-01 | 技术风险 | 没考虑实现可行性、复杂度或性能影响 | 补充技术风险评估 |
| PM-RISK-02 | 用户风险 | 方案可能对用户产生负面影响未说明 | 补充用户影响评估和 mitigation |
| PM-RISK-03 | 业务风险 | 没考虑对业务指标、收入、品牌的影响 | 补充业务风险评估 |
| PM-RISK-04 | 不确定性标注 | 把推测当事实写（"这将提升留存" vs "预计可提升留存"） | 区分事实/推断/假设 |
| PM-RISK-05 | 隐私与合规 | 涉及用户数据但未考虑隐私/法规要求 | 标注合规需求并确认法务 |

### 6. 表达层

| Gate | 校验目标 | 失败条件 | 处理 |
|------|---------|---------|------|
| PM-WRITE-01 | 可扫描 | 缺少标题层级、列表、加粗等结构，读者无法快速定位 | 增加结构化排版 |
| PM-WRITE-02 | 术语一致 | 同一概念在不同位置换名（如"用户"vs"客户"vs"使用者"） | 统一术语表 |
| PM-WRITE-03 | 建议可行动 | 结论或建议模糊（"后续跟进"vs"下周二前由 XX 确认 YY"） | 写明谁、做什么、什么时候 |
| PM-WRITE-04 | 表达直接 | 大量修饰语、被动语态、免责声明弱化了核心信息 | 删冗余，核心信息直接表达 |
| PM-WRITE-05 | 受众适配 | 给工程看的用了业务黑话，给高管看的用了技术细节 | 按读者调整表达层级 |
| PM-WRITE-06 | PRD 不要过界 | PRD 写了实现方式而不是需求是什么 | 区分 what 和 how |

### 7. 审计层

| Gate | 校验目标 | 失败条件 | 处理 |
|------|---------|---------|------|
| PM-APP-01 | 决策日志 | 重要决策没有记录原因和备选 | 补充决策记录 |
| PM-APP-02 | 开放问题 | 已知的不确定性没有列出 | 补充 open questions 及 owner |
| PM-APP-03 | 引用链接 | 引用的文档、数据、设计稿没有链接或链接失效 | 补充或修复链接 |
| PM-APP-04 | 版本记录 | 缺少变更历史，读者不知道哪个版本是最新的 | 补充版本日志 |

## 跨领域质量维度（每份文档都应扫描）

| 维度 | 检查要点 |
|------|---------|
| 可行动性 | 读者读完知道下一步做什么、谁做、什么时候做完？ |
| 用户中心 | 判断和决策中用户视角是否被充分考虑？ |
| 可衡量 | 成功标准是否量化，是否知道"做完了"和"做好了的区别？ |
| 风险透明 | 不确定性、风险、假设是否明确标注而非隐藏？ |
| 公平与包容 | 方案是否对不同用户群体都有考虑，有无不当概括？ |

## 错误分类与修复优先级

| 编码 | 类别 | 含义 | 优先级 |
|------|------|------|--------|
| POS | 定位错误 | 读者/边界/问题不对 | P0 |
| PROD | 基线缺陷 | 问题-方案-metrics 未闭环 | P0 |
| ANA | 分析缺陷 | 数据→结论断层 | P1 |
| EVD | 支撑不足 | 断言无依据 | P1 |
| RSK | 风险遗漏 | 未识别的风险或越界 | P1 |
| WRT | 表达问题 | 结构/术语/行动性差 | P2 |
| APP | 审计缺失 | 决策日志/版本/引用缺失 | P2 |
| SEC | 隐私/合规 | 数据或合规风险 | P0 |

## 质量等级

| 等级 | 条件 | 含义 |
|------|------|------|
| A（可交付） | 无 ❌，⚠️ ≤2 | 直接使用或微小调整 |
| B（需修改） | 无 ❌，⚠️ ≤5 | 修改后交付 |
| C（需重写部分） | ❌ ≤2，或定位/基线层未通过 | 部分重写 |
| D（需全面重写） | ❌ ≥3，或多层未通过 | 全面重写 |

**场景门槛：**

| 场景 | 最低接受 | 备注 |
|------|---------|------|
| 个人草稿 | C | — |
| 团队内部评审 | B | — |
| 跨部门/向高管汇报 | A | — |
| 客户/对外交付 | A | — |
| 涉及用户数据/合规 | A + SEC 必须 ✅ | — |

## 团队一致性机制

### 评估准则版本管理

```
v1.0 → 使用 2 周 → 校准会议 → v1.1 → 使用 1 月 → 校准 → v2.0
```

### 校准会议（新成员/新准则/出现分歧时）

```
1. 选取 3-5 份典型文档（好/中/差各等级）
2. 每人独立评分
3. 对比差异，分差 >1 级的门禁重点讨论
4. 修正准则措辞
5. 频率：新团队每周，成熟团队每月
```

### 分歧仲裁

```
两人分歧 → 第三人独立评分 → 取中位数 → 分歧记录到准则改进日志
```

### 质量趋势追踪

| 周期 | 平均等级 | P0/P1 数 | 主要问题类型 |
|------|---------|---------|-------------|
| Sprint 1 | B | 3 | ANA, EVD |
| Sprint 2 | B+ | 2 | EVD, WRT |
| Sprint 3 | A- | 1 | WRT |

## PM 检查原则

1. **问题先于方案** — 如果文档没有先说清楚"为什么做"，后面的所有内容都不成立。
2. **一条主张，一个依据** — 每个断言性陈述都应有数据、研究或用户反馈支撑。
3. **没有 metrics 就没有完成标准** — "做完了"和"做好了"的区别在于可衡量的标准。
4. **Scope 纪律是 PM 的命** — out-of-scope 比 in-scope 更重要，它是防止 scope creep 的唯一防线。
5. **不确定性要说出来** — 假设、风险、开放问题不应隐藏，标注它们是对团队负责。
6. **读者不看你的文档你也有责任** — 文档结构决定读者是否愿意读，标题要引导、段落要扫描、结论要靠前。
7. **决策日志就是团队记忆** — 不记录决策原因的团队，三个月后会在同一个问题上再吵一次。
