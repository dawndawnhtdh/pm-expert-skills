# AI Agent / Skill 开发管理指南（PM 工作手册）

## 定位

本文档是产品经理管理 AI agent / Claude Code skill 开发项目的操作指南。不是技术文档，而是**PM 流程文档**——告诉你怎么定义、验收、迭代一个 AI agent 项目，确保团队协作有标准、开发进度可追踪、交付质量可衡量。

---

## 三层结构总览

```text
┌─────────────────────────────────────────────────────┐
│  第一层：产品本体（SKILL.md）                        │
│  这是 AI 读的 — 业务逻辑、流程、规则、输出规范        │
│  负责人：开发/实施人员                               │
├─────────────────────────────────────────────────────┤
│  第二层：管理文档（本文档覆盖的）                      │
│  这是人读的 — 需求、验收标准、测试用例、版本日志       │
│  负责人：产品经理                                    │
├─────────────────────────────────────────────────────┤
│  第三层：流程工具（ai-quality-checker + Git）          │
│  这是"闸门" — 验证质量、管理版本、追踪问题             │
│  负责人：全员                                        │
└─────────────────────────────────────────────────────┘
```

**核心原则：**
- 第一层（SKILL.md）**只放业务逻辑**，不放管理内容
- 第二层（本文档衍生品）**每个 skill 一套**，随 skill 版本更新
- 第三层（流程）**团队一套**，跨所有 skill 共用

---

## 一、Skill PRD 模板

每个 AI agent / skill 项目开始前，PM 先写一份 PRD。以下是标准模板：

```markdown
# Skill: {名称} — 产品需求文档

## 1. 问题定义
{用 2-3 句话说明为什么要做这个 skill。什么场景下，谁有什么痛点？}

示例：
分析师写报告太慢，新手需要 6 个月才能写出可用报告。
质量不稳定——同一份材料不同分析师产出差异大，客户投诉增加。

## 2. 目标用户
{谁会用这个 skill？}

示例：
- 主要用户：社媒情报分析师（1-3 年经验）
- 次要用户：安全咨询顾问需要快速生成简报
- 非目标：决策者（他们是报告的读者，不是使用者）

## 3. 输入与输出

| 项目 | 说明 |
|------|------|
| 输入 | {用户提供什么？原始材料？事件描述？已有报告？} |
| 输出 | {生成什么？报告？JSON 配置？检查结果？} |
| 触发方式 | {slash command？自动触发？API 调用？} |

示例：
输入："监测法国大选期间社交媒体态势"
输出：结构化的社媒监控配置 JSON
触发方式：Claude Code 中 /SI-topic-monitor 命令

## 4. 功能需求

{按优先级列出功能，标注 P0/P1/P2}

| 优先级 | 需求 | 说明 |
|--------|------|------|
| P0 | 输入校验 | 用户输入不满足条件时返回错误 |
| P0 | 关键词生成 | 根据事件生成各平台检索关键词 |
| P1 | 多语言覆盖 | 支持监控主体所在国语言 |
| P2 | 时间建议 | 根据事件阶段建议监控时间窗口 |

## 5. 验收标准（Acceptance Criteria）

{可验证的通过条件，每条独立可测}

| # | 标准 | 验证方式 | 优先级 |
|---|------|---------|--------|
| AC-01 | 输入不含国家时返回 no_country 错误 | 输入"监测大选期间态势"→ 验证正确报错 | P0 |
| AC-02 | topic_name 使用事件涉及国官方语言 | 输入法国事件 → topic_name 为法语 | P0 |
| AC-03 | 输出 JSON 包含 4 个必填字段 | 用 JSON Schema 校验 | P0 |
| AC-04 | 输出不得出现"监测"类通用词 | 关键词检查 | P1 |

## 6. 非目标（Out-of-Scope）

{明确不做什么，防止 scope creep}

示例：
- 不提供实时数据采集（skill 只生成配置，不采集数据）
- 不替代人工分析判断（skill 辅助配置生成，不做分析结论）
- 本版本不支持英语事件输入

## 7. 使用限制

{已知限制，用户须知}

示例：
- 事件描述必须包含地理位置和事件类型
- 不支持纯英文输入（v1.0 限制）
- 不适用于品牌/企业监控场景（仅限政务/事件监控）
```

## 二、测试用例模板

验收标准确定后，转化为可执行的测试用例：

```markdown
# Skill: {名称} — 测试用例

## TC 组 1：基本功能（对应 AC-01 ~ AC-03）

### TC-01：正常输入
- 输入："监测柬埔寨大选期间社交媒体态势"
- 预期输出：JSON 包含 topic_name（高棉语）、4 个平台关键词、监控时间、分析主体
- 验证方法：JSON Schema 校验 + 人工检查语言
- 状态：☐ 通过 ☐ 未通过

### TC-02：边界情况 — 缺少国家
- 输入："监测大选期间社交媒体态势"
- 预期输出：{ "error": true, "valid": false, "reason": "no_country" }
- 验证方法：断言 error = true
- 状态：☐ 通过 ☐ 未通过

### TC-03：边界情况 — 输入太短
- 输入："大选"
- 预期输出：{ "error": true, "valid": false, "reason": "too_short" }
- 验证方法：断言 reason = too_short
- 状态：☐ 通过 ☐ 未通过

## TC 组 2：质量标准（对应 AC-04 ~ AC-06）

### TC-04：输出格式合规
- 输入：正常输入
- 预期：JSON 完全符合 output schema
- 验证方法：用 ai-quality-checker 验证
- 状态：☐ 通过 ☐ 未通过
```

**管理建议：**
- 新 skill 至少 10-15 个测试用例
- 每次版本迭代时更新测试用例
- 测试用例就是你的"回归测试套件"

## 三、版本日志模板

```markdown
# {名称} 版本日志

## v1.1（2026-08-15）
### 新增
- 新增对英语事件输入的支持
- 新增 YouTube 平台关键词

### 修复
- 修复法语事件 topic_name 包含英文字符的问题
- 修复 since: 日期格式错误

### 变更
- 将最小输入长度从 8 调整为 6
- 更新了 no_country 判定逻辑：增加"国"字白名单

### 已知问题
- 缅甸语关键词召回率偏低（依赖 X 平台语义检索补偿）

---

## v1.0（2026-07-01）
### 初始版本
- 支持中/法/日/韩 4 种语言的事件输入
- 覆盖 X/Facebook/Instagram/TikTok/YouTube 5 个平台
- 5 项输入校验规则
- 输出 JSON Schema v1.0
```

**版本号约定（参考 Arthur.ai + FutureAGI）：**

| 版本位 | 变更类型 | 示例 |
|--------|---------|------|
| major | 行为或输出格式变化，不向后兼容 | v1.0 → v2.0 |
| minor | 新增能力，向后兼容 | v1.0 → v1.1 |
| patch | 修复 bug，无功能变化 | v1.1 → v1.1.1 |

## 四、开发流程（Skill 迭代工作流）

```text
阶段 1：需求
   PM 写 Skill PRD（问题定义 + AC）
   团队评审，确认需求
       ↓
阶段 2：开发
   实施人员写 SKILL.md + 参考文件
   开发过程中 PM 持续对齐
       ↓
阶段 3：验证
   用测试用例逐条验证
   用 ai-quality-checker 检查质量
   发现问题 → 打回阶段 2
       ↓
   通过？
    ├── 是 → 阶段 4
    └── 否 → 回阶段 2
       ↓
阶段 4：发布
   更新版本日志
   打 Git tag（v1.0.0）
   通知团队更新
       ↓
阶段 5：迭代
   收集使用反馈
   决定下一版需求
   回到阶段 1
```

**关键闸门（不可跳过）：**

| 闸门 | 位置 | 最低标准 |
|------|------|---------|
| PRD 评审 | 阶段 1→2 | 所有 P0 需求已定义，AC 可验证 |
| 质量检查 | 阶段 3 | ai-quality-checker 评级 ≥ B |
| 发布审批 | 阶段 3→4 | 测试用例通过率 100%（P0/P1） |
| 上线确认 | 阶段 4 | 版本日志已更新，通知已发出 |

## 五、skill 质量检查对接

在验证阶段，直接用 `ai-quality-checker` 检查 SKILL.md 本身的质量：

**用前对照表（验证前的自检）：**

```markdown
## SKILL.md 自检清单（发布前核对）

### 定位类
☐ 是否有明确的问题定义段落？
☐ 是否说明了谁应该用这个 skill？
☐ 是否说明了输入和输出格式？
☐ 是否说明了使用限制/不适用场景？

### 内容类
☐ 业务规则是否有依据（参考文件或外部来源）？
☐ 流程是否清晰，用户按步骤能走完？
☐ 输出格式是否有示例？
☐ 术语在全文中是否一致？

### 结构类
☐ YAML frontmatter 的 name 和 description 是否正确？
☐ 标题层级是否合理（一级、二级、三级）？
☐ 是否有代码块、表格帮助扫描？
☐ 文件路径引用是否有效？

### 边界类
☐ 是否说明了 skill 不能做什么？
☐ 输入校验规则是否完整？
☐ 错误输出格式是否定义？
```

## 六、完整的 skill 项目文件结构

对于一个生产级 AI agent / skill，建议的文件结构：

```text
my-skill/
├── SKILL.md                          # 产品本体（AI 读）
├── README.md                         # 人类读的安装和使用说明
├── install.sh / install.bat          # 安装脚本（如适用）
│
├── docs/                             # PM 管理文档（人读）
│   ├── PRD.md                        # 需求文档
│   ├── test-cases.md                 # 测试用例
│   └── CHANGELOG.md                  # 版本日志
│
├── references/                       # 参考文件（AI 读）
│   └── ...                           # 业务规则、口径、示例
│
└── agents/                           # 跨平台配置（如适用）
    └── openai.yaml
```

**分层责任：**

| 目录 | 谁维护 | 更新频率 | 给谁看 |
|------|--------|---------|--------|
| SKILL.md | 实施人员 + PM 审核 | 每次迭代 | AI |
| docs/PRD.md | PM | 每次迭代前 | 团队成员 |
| docs/test-cases.md | PM + QA | 每次迭代 | 验证人员 |
| docs/CHANGELOG.md | PM | 每次发布 | 团队 + 用户 |
| references/ | 实施人员 | 随内容更新 | AI |

## 七、常见问题和陷阱

### 陷阱 1：把管理内容写进 SKILL.md

```markdown
❌ 错误：
## 验收标准
- AC-01：输入校验通过率 100%
- AC-02：输出符合 Schema

✅ 正确：放在 docs/PRD.md 中，SKILL.md 只写业务逻辑
```

### 陷阱 2：没有测试用例直接上线

后果：PM 觉得"看起来不错"，但边界情况（空输入、异常字符、超长文本）全部崩溃。

### 陷阱 3：版本日志不更新

后果：三个月后不知道当前是什么版本，回退不知道回退到哪，新成员接手一脸懵。

### 陷阱 4：SKILL.md 和实际行为不一致

后果：PM 按 SKILL.md 理解能力，实际输出不对——信任破裂。
解法：每次修改 SKILL.md 后，用测试用例验证一遍。
