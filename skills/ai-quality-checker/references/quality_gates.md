# PM 质量门禁详解（含正反示例）

每个门禁的详细判断标准和典型正反示例。

---

## 1. 定位层（PM-POS）

### PM-POS-01：读者明确

不同读者需要不同结构：

| 读者 | 需要什么 | 不需要什么 |
|------|---------|-----------|
| 工程师 | 需求、边界条件、异常处理、验收标准 | 市场分析长篇、商业论证 |
| 设计师 | 用户问题、场景、成功标准 | 技术实现细节 |
| 高管 | 问题、策略价值、资源需求、风险 | 逐条功能清单 |
| 客户 | 价值、变化、时间线 | 内部决策过程 |

**不通过示例：** 一份给工程看的 PRD 花了 2 页写市场机会，但验收标准只有一行"功能正常工作"。

### PM-POS-02：问题先行

**不通过：** "我们要在首页加一个 AI 推荐模块。"

**通过：** "新用户 7 日留存率目前 30%，低于行业基准 45%。核心原因是新用户第一次打开 app 不知道看什么。我们计划通过个性化推荐降低用户找到感兴趣内容的时间成本。预期提升 7 日留存至 40%。"

### PM-POS-03：边界清晰

| 好的 out-of-scope | 差的 out-of-scope |
|------------------|------------------|
| 明确列出本期不做的事项 | 只有 in-scope，或者 out-of-scope 太笼统 |
| "本次不包含：个性化排序、社交分享、Android 端" | "本次不包含的范围后续再定" |

### PM-POS-04：上下文完整

**不通过：** 直接进入方案细节，没有背景说明。
**通过：** 开头一段："上季度我们上线了 V2.1 的搜索功能，但由于索引策略问题，长尾 query 的召回率下降了 15%。本文是在 V2.1 基础上做索引优化，不是重新设计搜索。相关决策记录见 #DEC-021。"

## 2. 产品基线（PM-PROD）

### PM-PROD-02：Metrics 明确对照表

| ❌ 模糊 | ✅ 可衡量 |
|---------|----------|
| "提升用户体验" | "NPS 从 40 提升至 50（6 个月内）" |
| "提高效率" | "客服处理时间从 8 分钟降至 4 分钟（Q3 结束前）" |
| "增加营收" | "付费转化率从 5% 提升至 7%（上线后 90 天）" |
| "降低流失" | "月流失率从 8% 降至 5% 以下（上线后第 2 个月达成）" |

每个指标建议包含：
- 当前基线（baseline）
- 目标值（target）
- 时间窗口（timeframe）
- 失败阈值（rollback condition）

### PM-PROD-03：有优先级

不通过：5 个功能需求并列，没有区分必须/应有/可有。
通过：标注 P0/P1/P2，说明取舍理由。

### PM-PROD-04：格式匹配

| 文档类型 | 推荐结构 |
|---------|---------|
| PRD | Problem → Goals & Metrics → Scope → Solution → Key Flows → Open Questions |
| 竞品分析 | 分析框架 → 各竞品对比 → 共同趋势 → 对我方启示 |
| 周报 | 本周关键结果 → 风险/阻塞 → 下周计划 |
| 决策文档 | 问题陈述 → 选项 → 评估框架 → 推荐 → 风险 |

## 3. 分析层（PM-ANA）

### PM-ANA-01：结论先行

**不通过：**

```
我们看了用户反馈、分析了后台数据、对比了竞品策略。用户的反馈集中在...
（500 字分析过程）...所以我们需要优化注册流程。
```

**通过：**

```
注册流程是当前最大的用户流失点（30% 用户在第二步放弃）。原因分析：
1. ... 2. ... 支撑数据见附录。
```

### PM-ANA-02：数据→判断闭环

**不通过：** "竞品 A 上线了 AI 推荐功能，我们也需要。"

**通过：** "竞品 A 上线 AI 推荐后，单用户会话时长提升了 25%。我们的推荐系统上次更新是 18 个月前，当前用户内容消费深度在下降。对标竞品效果，我们有必要升级推荐策略。"

### PM-ANA-03：替代方案

**不通过：** "方案 A 是唯一可行的路径。"

**通过：**

| 方案 | 投入 | 效果预期 | 风险 | 推荐理由 |
|------|------|---------|------|---------|
| A 自研 | 3 个月 2 人 | 灵活可控 | 开发周期长 | 长期最优 |
| B 采购 | 1 个月，$50k | 快速上线 | 定制受限 | 短期过渡 |
| C 不做 | 0 | 无变化 | 用户流失加速 | 不推荐 |

### PM-ANA-04：用户视角

**不通过：** "数据库写入压力大，需要改缓存策略。"

**通过：** "用户发布内容后需要等 3 秒才能看到，原因是写入链路没有加缓存。优化后应降至 0.5 秒以内。"

## 4. 支撑层（PM-EVD）

### 支撑可信度排序

| 可信度 | 依据类型 | PM 场景示例 |
|--------|---------|------------|
| 高 | 一手用户研究 | 用户访谈、可用性测试、调研数据 |
| 中高 | 产品数据分析 | 埋点数据、A/B 测试结果、转化漏斗 |
| 中 | 客服/支持数据 | 工单分类、用户反馈汇总 |
| 中低 | 竞品/市场报告 | 竞品上线了什么、第三方报告 |
| 低 | 个人判断/传闻 | "我听说"、"我认为用户会" |

**要求：** 核心主张必须有中高以上可信度依据，低可信度依据不能单独支撑关键决策。

## 5. 风险层（PM-RISK）

### PM-RISK-01~03：风险评估模板

| 风险 | 概率 | 影响 | 应对策略 |
|------|------|------|---------|
| 推荐算法准确度不达标 | 中 | 高 | 先做小范围 A/B 测试 |
| 数据库查询延迟增加 | 低 | 中 | 做性能基线测试 |
| 用户对新 UI 抗拒 | 中 | 中 | 灰度发布 + 用户教育 |

## 6. 表达层（PM-WRITE）

### PM-WRITE-06：PRD 不要过界对照表

| ❌ 写了"怎么做"（过界） | ✅ 写了"要什么"（正确） |
|------------------------|----------------------|
| "后端用 Redis 缓存" | "搜索结果应在 500ms 内返回" |
| "首页加一个弹窗" | "用户首次使用时需完成偏好设置" |
| "用 React Native 重写" | "iOS 和 Android 功能需同步上线" |
