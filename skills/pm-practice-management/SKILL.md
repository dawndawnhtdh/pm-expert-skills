# PM 实战管理方法论 · AI Agent 开发管理

## 定位

面向产品经理的 AI agent / Claude Code skill 开发管理指南。不是技术文档，而是**PM 的实操手册**——管理 AI 产品从定义到交付的全过程，确保团队协作有标准、进度可追踪、质量可衡量。

在 AI agent 开发中，PM 的角色从"写 prompt"升级为**定义标准、管理流程、把控质量**。

---

## 核心概念：AI Agent 开发的三层结构

```text
┌─────────────────────────────────────────────────────┐
│  第一层：产品本体（SKILL.md）                        │
│  这是 AI 读的 — 业务逻辑、流程、规则、输出规范        │
│  负责人：架构师/开发人员                            │
├─────────────────────────────────────────────────────┤
│  第二层：管理文档（PM 负责）                         │
│  这是人读的 — 需求、验收标准、测试用例、版本日志       │
│  负责人：产品经理                                   │
├─────────────────────────────────────────────────────┤
│  第三层：质量闸门（ai-quality-checker + Git）         │
│  验证质量、管理版本、追踪问题                        │
│  负责人：全员                                      │
└─────────────────────────────────────────────────────┘
```

**核心原则：** SKILL.md 只放业务逻辑，不放管理内容。管理文档独立维护，与 SKILL.md 同步版本。

---

## Skill 开发全流程

```text
阶段 1：需求
   PM 写 Skill PRD（问题定义 + 验收标准）
   团队评审，确认需求
       ↓
阶段 2：开发
   架构师写 SKILL.md + 参考文件
   开发过程中 PM 持续对齐
       ↓
阶段 3：验证
   用测试用例逐条验证
   用 ai-quality-checker 检查质量
   发现问题 → 打回阶段 2
       ↓
   通过？
    ├── 是 → 阶段 4
    └── 否 → 回阶段 2
       ↓
阶段 4：发布
   更新版本日志
   打 Git tag
   通知团队更新
       ↓
阶段 5：迭代
   收集使用反馈
   决定下一版需求
   回到阶段 1
```

### 关键闸门（不可跳过）

| 闸门 | 位置 | 最低标准 |
|------|------|---------|
| PRD 评审 | 阶段 1→2 | 所有 P0 需求已定义，AC 可验证 |
| 质量检查 | 阶段 3 | ai-quality-checker 评级 ≥ B |
| 发布审批 | 阶段 3→4 | 测试用例通过率 100%（P0/P1） |
| 上线确认 | 阶段 4 | 版本日志已更新，通知已发出 |

## 五套实战工具

### 工具一：Skill PRD 模板

每个新 skill 项目前，PM 先用此模板定义需求：

```markdown
# Skill: {名称} — 产品需求文档

## 问题定义
{谁在什么场景下有什么痛点，2-3 句}

## 目标用户
{主要用户、次要用户、非目标用户}

## 输入与输出
| 项目 | 说明 |
|------|------|
| 输入 | 用户提供什么？ |
| 输出 | 生成什么？ |
| 触发方式 | slash command / API / 自动 |

## 验收标准（Acceptance Criteria）
| # | 标准 | 验证方式 | 优先级 |
|---|------|---------|--------|

## 非目标（Out-of-Scope）
{明确不做什么，防止 scope creep}

## 使用限制
{已知限制，用户须知}
```

### 工具二：测试用例模板

```markdown
# {Skill 名称} — 测试用例

### TC-01：正常输入
- 输入：{典型输入}
- 预期输出：{期望结果}
- 验证方法：{怎么验证}
- 状态：☐ 通过 ☐ 未通过

### TC-02：边界情况
- 输入：{异常或边界输入}
- 预期输出：{期望的错误处理}
- 验证方法：{怎么验证}
- 状态：☐ 通过 ☐ 未通过
```

### 工具三：版本日志规范

| 版本位 | 变更类型 | 示例 |
|--------|---------|------|
| major | 行为或输出格式变化，不向后兼容 | v1.0 → v2.0 |
| minor | 新增能力，向后兼容 | v1.0 → v1.1 |
| patch | 修复 bug，无功能变化 | v1.1 → v1.1.1 |

### 工具四：质量验收标准

每份 skill 应生成对应的验收标准文档，包含：

| 要素 | 说明 |
|------|------|
| 评分维度 | 产品基线、分析深度、证据链、表述克制、可读性、工程合规 |
| 通过线 | 100 分制，≥80 分通过 |
| Blockers | 一票否决规则（强判断无来源、推测当事实等） |
| Golden Cases | 3-5 个典型验收场景 |
| 工程清单 | 输入校验、输出结构、附录完整性 |

### 工具五：团队校准机制

| 工具 | 频率 | 解决什么问题 |
|------|------|-------------|
| 校准会议 | 新规则启用/新成员加入/分歧出现 | 统一评分标准理解 |
| 分歧仲裁 | 两人评分不一致时 | 第三人独立评分取中位数 |
| 质量趋势追踪 | 每 sprint | 观察质量变化趋势 |
| 准则改进日志 | 每次校准后 | 持续迭代质量标准 |


## 常见陷阱

| 陷阱 | 表现 | 解法 |
|------|------|------|
| 管理内容写进 SKILL.md | SKILL.md 里有验收标准、版本记录 | 移到 docs/ 目录 |
| 没有测试用例直接上线 | 边界情况全部崩溃 | 至少 10 个测试用例再交付 |
| 版本日志不更新 | 三个月后不知道当前是什么版本 | 每次发布强制更新 CHANGELOG |
| 标准和实际不一致 | PM 按 SKILL.md 理解能力，实际输出不对 | 每次修改后重新验证 |
